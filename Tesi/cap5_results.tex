This chapter presents the experiments used to evaluate the scheduler. It focuses on naive order assignment with different numbers of missions per batch, comparing simulated makespan, MATLAB execution time, and the working hours of each resource. The reference data file is \texttt{WM\_Export dati\_16062026\_30062026.xlsx} and the simulations were tested on the 4th division of the dataset (mantaining every order on its original length).

\section{Naive mission assignment}
In naive assignment, orders are selected and assigned to resources without explicit workload balancing or optimization. Each batch is built using a fixed mission quota while keeping all missions of an order on the same resource.

The tests use batches of 20, 40, and 60 missions. In the plots, diamond markers show resource refill times; the test with 60 missions per batch has 19 refill times. MATLAB execution time measures computing time, while makespan measures the time needed to complete the activities in the simulated system. The two quantities therefore describe different aspects of the experiment.

\subsubsection{Test with 20 missions}
Of the three configurations, the one with 20 missions per batch requires the most scheduler calls. The nominal quota is about two or three missions per operator. Actual assignment must, however, keep each order on one resource, which limits how evenly the workload can be distributed.

Resources 1, 4, and 6 have the highest working times. Resource 4 reaches 9.3147 hours, while resource 7 has the lowest value, at 6.6242 hours. Large orders that cannot be split across resources contribute to the observed imbalance.

The persistent CTPN simulation takes 162.962 seconds to run in MATLAB and has a simulated makespan of 9.31 hours. Figure~\ref{fig:20missionifix} shows the simulation.

\subsubsection{Test with 40 missions}
With 40 missions per batch, the scheduler is called less often than in the previous configuration. For the same total number of missions, doubling the nominal batch size roughly halves the number of batches. The actual ratio depends on order composition and any incomplete final batch.

MATLAB execution time drops to 156.008 seconds, about 6.95 seconds less than in the test with 20 missions. This single observation is not enough to attribute the reduction only to the lower number of scheduler calls.

Working times for resources other than resource 2 range from 6.9086 to 8.0386 hours. Resource 2 reaches 9.8656 hours, giving a simulated makespan of 9.87 hours, which is higher than in the previous configuration. A more even workload among some resources therefore does not reduce overall completion time. Figure~\ref{fig:40missionifix} shows the corresponding simulation.

\begin{figure}[htbp]

    \label{fig:40missionifix}
\end{figure}

\subsubsection{Test with 60 missions}
For the same total number of missions, batches of 60 give about one third of the nominal batch count of the 20-mission case. Here too, the actual number of scheduler calls depends on batch composition.

MATLAB execution time is 156.742 seconds, close to the value for 40 missions. Working times range from 6.3925 hours for resource 7 to 9.2633 hours for resource 4. Simulated makespan is 9.26 hours, the lowest of the three tests, although the difference from the 20-mission case is small.

Increasing the number of missions per batch therefore does not consistently worsen makespan. The workload remains uneven, however, as expected from an assignment rule without explicit workload balancing. Figure~\ref{fig:60missionifix} shows the test result.

The differences between the highest and lowest working times are about 2.69, 2.96, and 2.87 hours for batches of 20, 40, and 60 missions, respectively. According to this indicator, neither configuration with larger batches improves workload balance compared with the 20-mission test.

The results show that batch size affects both workload distribution and makespan, but neither follows a steady trend as batch size increases. In these tests, batches of 40 missions give the lowest MATLAB execution time, while batches of 60 give the lowest simulated makespan. These observations describe the reported runs and are not enough, on their own, to identify the best batch size in general.
