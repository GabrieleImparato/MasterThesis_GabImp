This chapter describes how missions are assigned to resources. The system uses
\textit{eight} resources, each consisting of a human operator and a forklift.
All orders are known before the simulation starts. They are assigned
progressively, and every mission of an order stays with the same resource.

The policy organizes decisions through global batching steps. The parameter
$x$ sets the number of new missions added at each refill and, in the chosen
configuration, the number of global completions that triggers the next step.
New missions are added to any remaining work: $x$ is not an upper limit on the
total number of admitted missions.

The simulation keeps the resource state at each assignment step. A resource
with a mission in progress keeps its path and scheduled completion time.
A resource with an empty queue can receive new work starting from the time
it finished its previous work. The global decision time is therefore separate
from the local times at which new missions are inserted. The method builds an
offline schedule and can fill earlier gaps in each resource's timeline.

Execution is controlled by a Colored Timed Petri Net (CTPN), which represents
precedence constraints and resource reservation. The A* planner determines the
paths and durations of missions when they start. The Euclidean estimate is used
only to set order deadlines and assess whether they are met after execution.
It does not affect assignment, refill, or the conditions for starting missions.

The model assumes that the prepared data define feasible missions and that all
admitted missions are completed.

\section{Orders, missions and resources}
\label{sec:progetto-modello}

Let $\mathcal O=\{o_1,\ldots,o_N\}$ be the set of orders and
$\mathcal R=\{1,\ldots,R\}$ the set of resources, with $R=8$ in the reference
configuration. Each order $o$ contains a set of missions $\mathcal M_o$, with
$n_o=|\mathcal M_o|$ missions. A mission describes a movement from a pickup point
FROM to a destination TO. It has a code, a priority, and an associated order.

Each dataset row also receives a unique occurrence identifier. Two missions
with the same commercial code therefore remain separate activities. A mission
without an order identifier is treated as a separate order; rows without this
information are not grouped into a single order.

The set $\mathcal M_o^{\mathrm{adm}}$ contains the missions of an order retained
after data preparation. Completion in the following sections refers to this
set. Data preparation checks the required information and normalizes coordinates
before assignment. Any excluded rows remain outside the operational net.

\begin{nota}
    A Python script splits the company data by working day. Each order stays
    entirely within the same daily group. All orders for the day are known
    before the simulation starts.
\end{nota}

\subsection{Order--resource assignment constraint}

Let $r(o)$ be the resource that owns order $o$. The model requires
\begin{equation}
    r(m)=r(o),\qquad \forall m\in\mathcal M_o^{\mathrm{adm}}.
\end{equation}
The owner is chosen when the first mission of the order enters a queue.
This assignment remains unchanged even if the order spans several batching
steps. The order cannot be split across resources, but its missions can be
admitted in different batches.

A resource can own several orders, but executes one order at a time. From the
start of an order to the end of its sequence, the token remains reserved for
that order. Its missions are not interleaved with missions from other orders.

\subsection{Priorities and internal precedence}

Each mission $m$ has a numerical priority $p_m$. The internal order sequence is
\begin{equation}
    \pi_o=(m_{o,1},\ldots,m_{o,n_o^{\mathrm{adm}}}),\qquad
    p_{m_{o,i}}\geq p_{m_{o,i+1}},
\end{equation}
where $n_o^{\mathrm{adm}}=|\mathcal M_o^{\mathrm{adm}}|$.
Missions with equal priority keep their input order. A missing priority is
assigned the default value of one.

This rule applies only to missions within the same order. New compatible
orders are considered in the order in which they first appear in the dataset.
They are not sorted by mission count, estimated duration, distance, or deadline.
Pending missions from orders already assigned to a resource take priority over
starting new orders.

\section{Order assignment policy}
\label{sec:progetto-assegnazione}

The policy applies the compatibility and unique-assignment constraints introduced
in Section~\ref{sec:theory-eligibility}. It separates the admission of new work
from the dispatching of queued missions, as described in
Section~\ref{sec:theory-batch-queues}. The scheduler decides which activities to
add, while the CTPN determines when they can start.

\subsection{Compatibility of the whole order}

Let $\mathcal R_m\subseteq\mathcal R$ be the resources compatible with mission
$m$. For the whole order,
\begin{equation}
    \mathcal R_o=\bigcap_{m\in\mathcal M_o^{\mathrm{adm}}}\mathcal R_m.
\end{equation}
The present problem assumes $\mathcal R_o\neq\varnothing$ for every order.
The owner is chosen from this set, ensuring that it can execute the entire
sequence. The assignment is fixed at the first admission and kept during later
refills.

\subsection{Global batch and additive refill}

Let $k$ identify a batching step. The following sets are used:
\begin{itemize}
    \item $\mathcal A_k^{-}$: missions already admitted but not yet completed
    before the refill, including waiting and running missions;
    \item $\mathcal N_k$: new missions added during the refill;
    \item $\mathcal A_k^{+}$: admitted work after assignment.
\end{itemize}
New missions are separate from the remaining work, so
\begin{equation}
    \mathcal A_k^{+}=\mathcal A_k^{-}\cup\mathcal N_k,
    \qquad \mathcal A_k^{-}\cap\mathcal N_k=\varnothing,
    \label{eq:refill-insiemi}
\end{equation}
\begin{equation}
    |\mathcal N_k|\leq x,\qquad
    |\mathcal A_k^{+}|=|\mathcal A_k^{-}|+|\mathcal N_k|.
    \label{eq:refill-additivo}
\end{equation}
When at least $x$ assignable missions remain, the new refill batch contains
$|\mathcal N_k|=x$ missions. This is the global total to distribute across all
resources, not the number assigned to each resource. Remaining work does not
reduce the size of the new batch.
\begin{example}[Mission admission set]
    With seven missions still admitted and $x=20$, a full refill brings the
    admitted work to twenty-seven missions. Admission is not based on the
    number of free places within a fixed capacity.
\end{example}

Let $C_k$ be the number of completion events recorded in the execution pass
after assignment $k$. The completion counter is reset at the start of each pass.
When
\begin{equation}
    C_k=x
    \label{eq:trigger-refill}
\end{equation}
the engine pauses before starting further missions and calls the scheduler if
work remains to be assigned. An empty queue on a single resource does not
trigger a refill on its own.

The counter includes all completions processed during the pass, including
missions admitted earlier. It is not simply a count between two global times
on the final timeline, because new events can be inserted at earlier times.

\begin{nota}
    With an empty initial state, a first batch of $x$ missions, and a threshold
    of $x$ completions, the first refill occurs when the entire batch has
    finished. The procedure preserves any remaining work, but this does not
    mean that missions must be running at every batch boundary. With equal
    batch size and completion threshold and no initial remaining work, the
    same condition holds in later passes.
\end{nota}

\subsection{Distributing missions across resources}

The list scheduling principles in Section~\ref{sec:theory-list-scheduling} are
applied using the number of missions already admitted for each resource.
For each resource,
\begin{equation}
    q_r=|\{m\in\mathcal A:\ r(m)=r\}|,
\end{equation}
where $\mathcal A$ contains admitted missions that have not yet completed.
The count includes both any running mission and the missions waiting in the
queue.

Resources are considered starting with the lowest $q_r$, giving preference to
those with fewer assigned missions. Ties are resolved in favour of the resource
with fewer compatible unassigned orders. A resource that already owns an order
with missions still to be queued receives priority. Any remaining ties are
resolved by resource index. The number of compatible orders is computed at the
start of the step, while $q_r$ is updated after each new admission.

Once a resource is selected, the next mission is chosen using two rules:
\begin{enumerate}
    \item If an order already assigned to the resource has pending missions,
    select the first available one, respecting the order's internal precedence.
    \item If no owned missions remain to be queued, select the first compatible
    unassigned order in input order and admit its first pending mission.
\end{enumerate}
After each insertion, $q_r$ is updated. The procedure continues until the new
batch is full or no work remains available. Missions already in the queue keep
priority over those added later.

The rule distributes the number of admitted missions without estimating their
duration. It therefore guarantees neither equal processing workloads nor
continuous activity on every resource. Actual working time depends on mission
paths and the characteristics of the assigned orders.

\section{CTPN for resource reservation}
\label{sec:progetto-ctpn}

The model applies the timed coloured representation introduced in
Section~\ref{sec:theory-ctpn}, extending token reservation to the mission
sequence of a whole order.

Figure~\ref{fig:pn2vecchiamissioni} recalls the previous model, which
was organized around resource alternatives for a single mission. In the chosen
solution, the scheduler assigns a resource to the entire order when its first
mission is queued. The net uses the colour of the assigned resource instead
of selecting a new owner for every mission.


\begin{figure}[H]
    \centering
    \includegraphics[width=0.7\linewidth]{imgs/Cap2_teoria/NEW_PN2_VECCHIA_MISSIONI}
    \caption{Previous model of resource alternatives for a single mission.}
    \label{fig:pn2vecchiamissioni}
\end{figure}

\noindent Each mission keeps a subnet with three transitions and two internal places.
The three stages represent the start, timed completion, and either the move
to the next mission or the release of the resource. Subnets belonging to the
same order are connected in sequence according to internal priorities.

\subsection{Intra-order links}

A linking place is inserted between consecutive missions. It receives the token
from the final transition of one mission and makes it available to the initial
transition of the next. The token keeps the assigned resource's colour.
The linking place therefore represents both precedence and continued resource
reservation.

Figure~\ref{fig:pn1nuovamissioni} shows a sequence of three missions. Places
$P7$ and $P8$ connect their subnets. The diagram shows precedence and must be
read together with the constraint on resource colour.

\begin{figure}[H]
    \centering
    \includegraphics[width=0.7\linewidth]{imgs/Cap2_teoria/NEW_PN1_NUOVA_MISSIONI}
    \caption{Three missions of the same order connected by precedence places.
    The resource token moves through the sequence without returning to the
    common place between intermediate missions.}
    \label{fig:pn1nuovamissioni}
\end{figure}

Only the first mission of an order takes a token from the common place of
available resources; only the last admitted mission returns it. Within the
order, the token in the linking place provides the availability needed to start
the next mission. No additional free resource must be taken from the common
place.

For each resource $r\in\mathcal R$, the operational net contains exactly one
token of colour $r$. Token conservation is expressed by the place invariant
\begin{equation}
    \sum_{p\in\mathcal P}M(p)(r)=1,
    \qquad \forall r\in\mathcal R,
\end{equation}
where $M(p)(r)$ is the number of tokens of colour $r$ in place $p$, and
$\mathcal P$ is the set of net places. The marking determines which transitions
are enabled, while the order--resource assignment determines the colour allowed
to take part in their firing.

\begin{nota}
    The figures use ordinary Petri nets rather than CPN diagrams for clarity.
    Each figure shows a single branch carrying tokens of one colour, which
    allows a simpler graphical representation.
\end{nota}

\subsection{Refill resource-reservation}

Pausing for batching does not release the resource. A running resource's token
stays in the working place of its current mission. A token waiting for the next
mission of the same order stays in the linking place instead of returning to
the common place. The resource is released only when the order is complete.

Refill changes mission admission and assigns resources to new orders. It does
not rebuild the net, reset the marking, or recalculate the path of a mission
already in progress. A mission can start only if it has been admitted and its
CTPN transition is enabled.

\section{State continuity between batches}
\label{sec:progetto-tempo}

\subsection{Persistent state and running resources}

Between batching steps, the simulation preserves the \textbf{marking},
\textbf{order owners}, \textbf{remaining queues}, \textbf{resource positions},
\textbf{paths of started missions}, and their \textbf{start times} and
\textbf{scheduled completion times}. It also keeps the completion history and
any deadlines already set. The counter $C_k$ is reset for the new pass.

The \textit{in work} indicator counts resources with a mission that has started
but has not yet completed in the paused state. It excludes missions that are
only waiting. Since each resource executes one mission at a time, this also
equals the number of running missions.

\subsection{Execution events and the global threshold}

Execution follows the Scheduled Event List principle described in
Section~\ref{sec:theory-sel}. A mission $m$ starting at $s_m$ with duration
$\tau_m$ is scheduled to complete at
\begin{equation}
    c_m=s_m+\tau_m.
\end{equation}
The engine processes concurrent events and increments $C_k$ at each completion.
Until the threshold is reached, a resource can start its next admitted and
enabled mission without calling the scheduler.

When $C_k=x$, the engine saves the state before any further starts. Other events
scheduled at the same time are processed in the next pass, without adding a
physical delay. This convention keeps the completion count for each pass exact.

If no new missions remain to be admitted, the engine continues with the work
already assigned. The simulation ends when all missions admitted after data
preparation are complete. The final pass may contain fewer than $x$ completions
if the remaining work is below the threshold.

\subsection{Global decision and local restart}

The global decision time $T_k$ is separate from the time cursor $\theta$ used
to process events. Global decision times never decrease. The cursor, however,
can return to an earlier time to insert work on a resource's timeline.

For a resource with an empty queue, let $f_{r,k}$ be its last known completion
time before refill. New work can be inserted starting at
\begin{equation}
    a_{r,k}=f_{r,k},
    \label{eq:ripartenza-locale}
\end{equation}
even when $a_{r,k}<T_k$. For a resource that has not yet been used, the initial
time is zero. If the resource still has queued or running work, new additions
respect that work and do not move its execution to an earlier time.

\begin{example}[Back-to-the-Future assignment]
    A resource that emptied its queue at $80\,\mathrm{s}$ can receive its next
    batch starting at that time, even if the global decision is recorded at
    $120\,\mathrm{s}$. New work fills a previously empty part of its timeline.
\end{example}

\noindent Moving the cursor back does not undo events already fixed on other
resources. Each resource keeps its own progress: two missions cannot run at the
same time on one resource, and a mission already in work is not changed.
In particular, its completion time $c_m$ remains the value set when it started.

Events inserted at earlier times belong to the new processing pass. If the
cursor reaches the completion target at a time $\theta_k^{\mathrm{stop}}$
before the latest global decision, the next decision time is recorded as
\begin{equation}
    T_{k+1}=\max\{T_k,\theta_k^{\mathrm{stop}}\}.
    \label{eq:decisione-globale}
\end{equation}
This avoids imposing a single restart time on all resources and separates the
decision sequence from the final timeline.

\begin{nota}
    The procedure builds an offline schedule from known orders. Inserting work
    at earlier times fills the simulated timeline; it does not represent a
    command that a physical system could execute in the past. Program computing
    time is not added to simulated operating time.
\end{nota}

\section{Deadline estimate}
\label{sec:stima-deadline-euclidea}
\label{sec:stima-deadline-manhattan} % Alias kept for existing references.

Deadlines follow the definitions in Section~\ref{sec:theory-deadlines}.
They are evaluation indicators used to compare the geometric estimate with
completion times. They do not select orders, size queues, assign resources,
or trigger refills.

An order's deadline is set when its first mission actually starts. It is not
measured from owner assignment: waiting for earlier orders does not use up the
new order's time allowance. All cumulative deadlines for the order are fixed
together and are not recalculated during refills or when later missions resume.

\subsection{Sequence and estimated distance}

Consider the sequence $\pi_o$ of admitted missions, sorted by internal precedence.
The endpoints $F_i$ and $T_i$ are the grid indices of FROM and TO after
normalization and rounding. The estimate uses
\begin{equation}
    d_E(p,q)=\sqrt{(x_p-x_q)^2+(y_p-y_q)^2}.
    \label{eq:manhattan-distance} % Historical label kept for compatibility.
\end{equation}
Let $P_r$ be the resource position before the order starts. Set $Q_1=P_r$ and
$Q_i=T_{i-1}$ for $i>1$. If the resource has no previous position, set $Q_1=F_1$.
The estimated distance for each mission is
\begin{equation}
    \widehat\ell_{o,i}=d_E(Q_i,F_i)+d_E(F_i,T_i).
    \label{eq:estimated-order-distance}
\end{equation}
This includes the initial approach and travel between consecutive missions.
The estimate does not run A* or apply the planner's corrections to free and
reachable cells.\footnote{Euclidean distance is calculated using the same formula
used to estimate average travel time in the A* algorithm.}

With speed $v_c=5.5$ cells per second, an allowance $\alpha=0.20$, a fixed
additional time $\tau_f=60\,\mathrm{s}$, and a margin
$\delta_m=30\,\mathrm{s}$ per mission, the estimated duration is
\begin{equation}
    \widehat\tau_{o,i}=
    \operatorname{round}\!\left(
    \frac{\widehat\ell_{o,i}}{v_c}(1+\alpha)\right)
    +\tau_f+\delta_m.
    \label{eq:stima_scadenze}
\end{equation}
The margin is a configurable parameter of the deadline model. Each mission's
estimate is rounded before summation, and the margin is added per mission,
not once per order. The estimated order duration is
\begin{equation}
    \widehat D_o=\sum_{i=1}^{n_o^{\mathrm{adm}}}\widehat\tau_{o,i}.
    \label{eq:estimated-order-duration}
\end{equation}

Let $S_o$ be the time when the order first starts. Its cumulative deadlines are
\begin{equation}
    d_{o,i}=S_o+\sum_{j=1}^{i}\widehat\tau_{o,j},\qquad
    d_o=S_o+\widehat D_o.
    \label{eq:estimated-order-deadline}
\end{equation}
The order deadline is the deadline of its final mission.

\begin{nota}
	Geometry-based deadline estimates were introduced because a fixed
	allowance of 180 seconds per mission did not adequately capture
	the variability in execution times. Although the mean and median
	were approximately 180 seconds, individual durations varied
	considerably: some missions took about 60 seconds, whereas others
	exceeded seven minutes. A single nominal value could therefore
	overestimate the time required by shorter missions and underestimate
	that required by longer ones.
\end{nota}

\subsection{Estimate and execution}

The Euclidean estimate does not change the marking, transition enabling, or
path choice. Simulated duration comes from the points returned by A*, while
the estimate uses direct distances between the requested endpoints. The two
quantities therefore have different meanings, even when they share some time
coefficients.

Obstacles, detours, coordinate corrections, and rounding can create differences
between estimated and simulated durations. The estimate is not a guaranteed
lower or upper bound. Human behaviour is not described by an explicit stochastic
model. Time margins are calibration parameters and do not replace validation
against operational data.

    \subsection{Resource continuity and route planning}

    Each mission has two planned legs: from the current resource position to
    FROM, and from FROM to TO. The second leg starts at the point actually
    reached by the first, keeping movement continuous. After completion, the
    actual TO becomes the resource's starting position for its next mission.

    A resource that has not yet worked is initially placed at the FROM of its
    first mission. Travel from a common depot is not modelled. If this position
    is occupied, the nearest free cell is selected. An occupied FROM is corrected
    within the component reachable from the resource position. For the missions
    considered, a free FROM is assumed to be reachable from that position.
    The planner does not automatically change FROM when its cell is free.

    Paths are found with A* on the static map, following the heuristic search
    principle introduced in~\cite{hart1968formal}. The model does not represent
    other vehicles' occupancy over space and time. Resources running concurrently
    therefore do not imply that collisions between their paths are checked.

    Simulated duration is calculated from the A* path combining the approach
    leg and the FROM--TO leg. If $K_m$ is the number of points in the combined

        \tau_m=\operatorname{round}\!\left(\frac{K_m}{5.5}(1+0.20)\right)+60
        \quad [\mathrm{s}].

    both. It is not the sum of Euclidean edge lengths: a diagonal step also
    contributes through the point count. The fixed term represents additional
    operations.

    Duration excludes waiting before the start and is not capped at the nominal
    reference of 180 seconds. It is a model estimate, separate from both the
    deadline estimate and a physical measurement.

\section{Performance indicators}
\label{sec:progetto-indicatori}

\subsection{Completions, new admissions and remaining work}

The report distinguishes new admissions $|\mathcal N_k|$, remaining work
$|\mathcal A_k^{-}|$, and completions $C_k$ in each pass. Missions kept across
several boundaries are not counted again as new assignments or new completions
in each pass.

The number of scheduler calls measures actual assignment steps. There is at
most one call per pass, while simply completing already admitted work requires
no new assignment. The report also records the global decision time, the cursor
restart time, and local insertion times. Global lines and resource markers in
the plots represent these different quantities.

\subsection{Resource utilization on the final timeline}

Resource busy time is calculated on the final timeline, including work inserted
at earlier times. Between consecutive decisions at $T_k$ and $T_{k+1}$, only
time actually spent working within that interval is counted. If a mission
starts before or ends after the interval, only the part inside it is included.

Let $W_{r,k}$ be the busy time and $L_k=T_{k+1}-T_k$ the interval duration.
Resource idle time and utilization are
\begin{equation}
    I_{r,k}=L_k-W_{r,k},\qquad
    U_{r,k}=\frac{W_{r,k}}{L_k}\quad\text{if }L_k>0.
    \label{eq:occupazione-timeline}
\end{equation}
For example, a resource working for 45 minutes in a one-hour interval has
$75\%$ utilization and 15 minutes of idle time. For zero-duration intervals,
the report sets utilization to zero.

The report also measures work completed within the nominal reference
$D_k=T_k+H$. This amount, $W_{r,k}^{\mathrm{slot}}$, includes only busy time
between $T_k$ and the earlier of $T_{k+1}$ and $D_k$. The corresponding
utilization is $U_{r,k}^{\mathrm{slot}}=W_{r,k}^{\mathrm{slot}}/H$.
Any overrun beyond the reference is measured by
$\Delta_k=\max\{0,T_{k+1}-D_k\}$.
These values describe the simulation result and do not determine when refill
occurs.

\subsection{Slack and delay relative to deadlines}

As defined in the previous chapter, the completion margin shows how early or
late completion is relative to the deadline, while \textit{tardiness} measures
only delay. For missions and orders,
\begin{equation}
    \begin{aligned}
        \sigma_{o,i}&=d_{o,i}-c_{o,i}, &
        T_{o,i}&=\max\{0,c_{o,i}-d_{o,i}\},\\
        \sigma_o&=d_o-C_o, &
        T_o&=\max\{0,C_o-d_o\}.
    \end{aligned}
\end{equation}
A positive margin means early completion; a negative margin means delay.
A mission's delay can be recovered before the order finishes. These indicators
assess whether deadlines are met without changing scheduler decisions.
