\section{Scheduled Event List}

Once the warehouse operations have been represented as discrete events, it is
necessary to determine how these events evolve during the simulation. A useful
technique for this purpose is the \textit{Scheduled Event List} (SEL), which
provides a mechanism for managing the events that may occur as the state of the
system changes, following the discrete-event simulation framework described
in~\cite{cassandras2021des}.

The basic idea is to associate each feasible event with the instant of time at
which it is expected to occur. Considering a set of events $E$ and a state space
$X$, at a given state $x \in X$ only a subset of events is feasible. This subset
can be denoted by $\Gamma(x)$. Each feasible event $i \in \Gamma(x)$ is associated
with a clock value $y_i$, representing the amount of time remaining before that
event occurs.

The next event to be executed is therefore the feasible event characterized by
the smallest clock value:

\begin{equation}
	e' = \arg\min_{i \in \Gamma(x)} y_i
\end{equation}


\noindent Consequently, the amount of time spent in the current state is

\begin{equation}
	y^* = \min_{i \in \Gamma(x)} y_i
\end{equation}

\noindent and the simulation time can be updated according to

\begin{equation}
	t' = t + y^*
\end{equation}

\noindent Instead of explicitly maintaining the remaining clock value of every event, the
simulation can store the events together with their scheduled execution times.
The resulting Scheduled Event List can be represented as

\[
L = \{(e_k,t_k)\},
\]

\noindent where $e_k$ represents an event and $t_k$ the corresponding scheduled execution
time.

The evolution of the simulation can then be described as an iterative procedure.
First, the event having the smallest scheduled time is extracted from the SEL
and executed. The simulation clock is advanced to the corresponding event time
and the state of the system is updated. As a consequence of this state change,
some previously scheduled events may no longer be feasible and are therefore
removed from the list, while newly enabled events are inserted. Finally, the SEL
is reordered according to the scheduled execution times before starting the next
iteration.

	\centering
	\includegraphics[width=1\linewidth]{imgs/Cap2_teoria/SEL_generalized}
	\caption{Generalized Scheduling Event scheme in computer simulations}
	\label{fig:selgeneralized}
\end{figure}


In the warehouse scheduling problem, this mechanism is particularly useful
because the feasibility of a mission depends on the current state and on the
availability of the resources required to execute it. For example, a loading
operation requiring both a forklift and an operator cannot start until both
resources are available. When another mission is completed and those resources
are released, the state of the system changes and the loading operation may
become feasible and consequently enter the SEL.

The SEL should therefore not be interpreted as a static schedule generated once
at the beginning of the simulation. It is a dynamic structure that evolves
together with the system. This is particularly important when several missions
compete for shared resources, since every completed operation may modify the set
of missions that can subsequently be executed.

In this framework, the SEL provides the temporal mechanism required to determine
\textit{when} events occur. However, an additional model is required to represent
the state of the system, the availability of resources, the dependencies between
operations, and the conditions under which an event becomes feasible. Petri nets
provide a suitable formalism for this purpose.


\section{Petri Nets}

Warehouse operations are characterized by a high degree of concurrency. Several
missions may be active at the same time, different resources may operate
simultaneously, and multiple activities may compete for the same limited
resources. A model used to represent such a system must therefore describe not
only the individual evolution of each mission, but also synchronization,
concurrency, resource availability, and conflicts among different activities.

\textit{Petri nets} (PNs) are a discrete-event modeling formalism particularly
suited to representing these characteristics. A Petri net is a directed bipartite
graph composed of two different types of nodes: \textit{places} and
\textit{transitions}. Places can represent conditions, states, or the availability
of resources, whereas transitions represent events or operations that modify the
state of the system. Places and transitions are connected through directed arcs.
The terminology and firing rules used here follow the formulation
in~\cite{cassandras2021des}; the use of Petri-net models
for simulation and control is also discussed
in~\cite{basile2007pnetlab}.

The current state of a Petri net is described by its \textit{marking}, namely the
distribution of \textit{tokens} among the places of the net. A transition is
enabled only when its input places contain the tokens required for its execution.
When an enabled transition fires, the corresponding input tokens are consumed
and new tokens are produced in its output places, according to the structure of
the net.

This mechanism naturally represents resource allocation. For example, consider
a warehouse mission that requires both a forklift and an operator. Two places
may represent the availability of these resources. The transition corresponding
to the beginning of the mission can fire only when both places contain the
required tokens. Once the transition fires, the tokens are removed, representing
the fact that the forklift and the operator are currently busy. At the completion
of the mission, another transition can return the tokens to the corresponding
resource-availability places, making them available for subsequent missions.

This representation becomes particularly useful when several missions compete
for the same resources. If two missions require the same forklift, for example,
the availability of a single token prevents both corresponding transitions from
acquiring that resource simultaneously (fig. \ref{fig:pn}). Resource conflicts can therefore be
represented directly through the structure and marking of the net.

\noindent Compared with a representation based exclusively on finite-state machines,
Petri nets provide a natural way to describe several concurrent activities within
the same model. This characteristic is especially relevant in warehouse systems,
where many missions may evolve simultaneously and their execution may depend on
shared resources.

Petri nets can also be represented mathematically through incidence matrices.
In particular, the \textit{Pre} and \textit{Post} matrices describe the
connections from places to transitions and from transitions to places,
respectively. This representation is particularly useful when the model has to be
automatically generated, simulated, or integrated into an optimization algorithm.

From a mathematical point of view, a Place/Transition Petri Net can be defined
as the four-tuple $N = (P,T,Pre,Post)$ where $P$ is the set of places, $T$ is the set of transitions, while $Pre$ and $Post$ describe the connections between places and transitions.

The structure of the net can also be represented through the incidence matrix

\begin{equation}
	C = Post - Pre
\end{equation}

\noindent The state of the system is represented by the \textit{marking} $m$, which
specifies the number of tokens contained in each place. A transition $t$ is
enabled only if all its input places contain the required number of tokens:

\begin{equation}
	m(p) \geq Pre(p,t),
	\qquad \forall p \in {}^\bullet t
\end{equation}

\noindent When an enabled transition fires, the marking of the Petri Net changes according
to the tokens consumed and produced by the transition. More generally, the
evolution of the marking after a sequence of transition firings can be expressed
through the state equation

\begin{equation}
	m = m_0 + C\sigma
\end{equation}

\noindent where $m_0$ is the initial marking and $\sigma$ is the firing-count vector,
whose elements indicate how many times each transition has fired.

\subsection{Colored Petri Nets}

When the system contains a large number of missions and several similar resources,
a standard Petri-net representation may become increasingly complex. A useful
extension is represented by \textit{Colored Petri Nets} (CPNs), which introduce
different types of tokens, generally referred to as \textit{colors}. The
PN/CPN modeling framework is discussed
in~\cite{basile2007pnetlab}.

The use of colors makes it possible to distinguish different resources or
operational conditions while preserving the general structure of the Petri net.
In a warehouse scenario, for example, different colors can be associated with
different operators, forklifts, or other resources involved in mission execution.
In this way, multiple resources can evolve simultaneously through the same model
without losing information about which specific resource is performing a given
task.

Formally, a Colored Petri Net can be defined as the six-tuple

\[
N=(P,T,Pre,Post,Cl,Co),
\]

\noindent where $P$ is the set of places, $T$ is the set of transitions, $Cl$ is the set
of colors, and $Co : P \cup T \rightarrow Cl$ is the color function that associates each place and transition with an ordered
set of admissible colors.

For a place $p_i \in P$, the set of possible token colors can be expressed as

\begin{equation}
	Co(p_i)=\{a_{i,1},a_{i,2},\dots,a_{i,u_i}\}\subseteq Cl,
\end{equation}

\noindent while, for a transition $t_j \in T$, the corresponding set of occurrence
colors is

\begin{equation}
	Co(t_j)=\{b_{j,1},b_{j,2},\dots,b_{j,v_j}\}\subseteq Cl.
\end{equation}

\noindent Unlike a standard Petri Net, in which the marking of a place is represented only
by the total number of tokens, in a CPN the marking must also preserve information
about their colors. Therefore, the marking of a place $p_i$ can be represented
by the vector

\[
m_i =
\begin{bmatrix}
	m_i(1)\\
	m_i(2)\\
	\vdots\\
	m_i(u_i)
\end{bmatrix},
\]

\noindent where $m_i(h)$ represents the number of tokens of color $a_{i,h}$ contained in
place $p_i$. The complete marking of the CPN is consequently obtained by
collecting the markings of all places:

\[
m =
\begin{bmatrix}
	m_1\\
	m_2\\
	\vdots\\
	m_{|P|}
\end{bmatrix}.
\]

\noindent This additional information is particularly useful for warehouse optimization.
For example, if several operators are available, each operator can be associated
with a different token color. When a transition corresponding to a mission fires,
the color involved in that transition identifies the particular resource assigned
to the mission.

As in standard Petri Nets, the structural evolution of the system is described
through the incidence matrix

\[
C = Post - Pre.
\]

\noindent However, in a CPN the entries of the $Pre$ and $Post$ matrices also depend on the colors associated with places and transitions.

Considering a transition $t_j$ with occurrence color $b_{j,k}$, the transition
is enabled only if the required number of tokens of each color is available in
its input places:

\begin{equation}
	m_i(h) \geq Pre(p_i,t_j)(h,k).
\end{equation}

\noindent If the transition fires, the marking is updated according to

\begin{equation}
	m_i'(h)
	=
	m_i(h)
	+
	Post(p_i,t_j)(h,k)
	-
	Pre(p_i,t_j)(h,k).
\end{equation}

\noindent These equations show why the introduction of colors is particularly useful in a
resource-allocation problem. The enabling of a transition does not depend only
on the total availability of resources, but also on the availability of the
specific type or identity of resource required by that operation.

For instance, if a mission requires a particular forklift and an available
operator, the corresponding transition can be enabled only when the appropriate
tokens are present in the required places. Once the transition fires, those
tokens are consumed or moved, representing the fact that the corresponding
resources are currently allocated to the mission. When the operation is completed,
the resources can be released and become available again for other missions.

As a consequence, Colored Petri Nets allow the simulation to keep track of the
usage and identity of individual resources while maintaining the main advantages
of standard Petri Nets in representing concurrency, synchronization, and resource
conflicts. This makes them particularly suitable for resource-allocation and
scheduling problems involving a large number of simultaneous warehouse operations.

\section{Scheduling basics}
\label{sec:scheduling-basics}

Scheduling concerns the allocation of a set of activities to a limited set of
resources and the definition of their execution over time. In its classical
formulation, a scheduling problem specifies the activities to be processed, the
resources that can execute them, the technological or precedence constraints,
and one or more performance criteria used to evaluate the resulting schedule.
For the allocation layer, a relevant reference is the online machine
load-balancing framework presented in~\cite{aspnes1997online}: jobs are
assigned irrevocably as they arrive, with the objective of minimizing the
maximum accumulated machine load. This provides a useful abstraction for
order assignment; the warehouse model additionally includes resource
compatibility, mission dependencies, and spatial constraints.

In the warehouse problem considered in this work, the natural scheduling unit is
not the single mission alone, but the \textit{order}. An order groups several
missions that belong to the same logical request and must preserve a common
resource ownership during their execution. Let

\begin{equation}
	\mathcal{O}=\{1,2,\ldots,N_O\}
\end{equation}

\noindent be the set of orders and let

\begin{equation}
	\mathcal{M}_o=\{m_{o,1},m_{o,2},\ldots,m_{o,n_o}\}
\end{equation}

\noindent denote the set of missions belonging to order $o$, where $n_o$ is the
number of missions contained in that order. The available resources are denoted
by

\begin{equation}
	\mathcal{R}=\{1,2,\ldots,N_R\}.
\end{equation}

The problem can therefore be interpreted as a parallel-resource scheduling
problem with eligibility constraints, grouped operations, and limited resource
capacity. At most one activity can use the same resource at a given instant, and
an order can be assigned only to a resource that is compatible with all of its
missions.

\subsection{Eligibility constraints and order-level assignment}

Not every resource is necessarily able to execute every mission. For each
mission $m$, let $\mathcal{R}_m\subseteq\mathcal{R}$ be the set of resources that
satisfy the required compatibility conditions. Since all missions belonging to
the same order must preserve the same owner, the resources admissible for the
whole order are obtained by intersecting the eligibility sets of its missions:

\begin{equation}
	\mathcal{R}_o
	=
	\bigcap_{m\in\mathcal{M}_o}\mathcal{R}_m.
	\label{eq:order-eligible-resources}
\end{equation}

\noindent If $\mathcal{R}_o=\varnothing$, the order cannot be assigned without violating
at least one compatibility requirement. Otherwise, the assignment decision can
be represented by the binary variable

\begin{equation}
	x_{or}=\begin{cases}
		1, & \text{if order }o\text{ is assigned to resource }r,\\
		0, & \text{otherwise.}
	\end{cases}
\end{equation}

\noindent The unique-assignment constraint is then

\begin{equation}
	\sum_{r\in\mathcal{R}_o}x_{or}=1,
	\qquad \forall o\in\mathcal{O},
	\label{eq:unique-order-assignment}
\end{equation}

\noindent with $x_{or}=0$ for every $r\notin\mathcal{R}_o$. Consequently, if resource
$r$ is selected for order $o$, the same assignment is inherited by all missions
$m\in\mathcal{M}_o$. This differs from a mission-by-mission allocation, in which
the missions of the same order could be distributed among different resources.
The order-level constraint preserves operational continuity and is consistent
with the token reservation mechanism represented by the Colored Petri Net.

\subsection{Greedy load balancing and list scheduling}

A complete combinatorial optimization of all possible order--resource
associations can become expensive as the number of orders grows. A common
alternative is a \textit{list-scheduling} heuristic: orders are considered
sequentially and each order is assigned using the information available at that
step. Sequential processing of a known list is not, by itself, an online
problem: the online interpretation applies when decisions must be made without
knowledge of future orders. The rule below is a baseline greedy assignment
heuristic, rather than an implementation of the algorithms proposed
in~\cite{aspnes1997online}.

Let $L_r$ denote the workload already assigned to resource $r$. In the simplest
case, when no reliable processing-time estimate is yet available, the workload
can be approximated by the number of missions already assigned to the resource:

\begin{equation}
	L_r
	=
	\sum_{o\in\mathcal{A}} n_o x_{or}.
	\label{eq:resource-load-mission-count}
\end{equation}

\noindent Here $\mathcal{A}\subseteq\mathcal{O}$ contains only the orders already
assigned at the current decision step; initially $\mathcal{A}=\varnothing$.
When a new order $o$ has to be assigned, a load-balancing rule selects the
least-loaded compatible resource:

\begin{equation}
	r_o^{\star}
	=
	\arg\min_{r\in\mathcal{R}_o} L_r.
	\label{eq:least-loaded-assignment}
\end{equation}

\noindent Ties must be resolved using a fixed resource ordering to make the
rule deterministic. After the decision, $o$ is added to $\mathcal{A}$ and the
corresponding load is updated according to

\begin{equation}
	L_{r_o^{\star}}
	\leftarrow
	L_{r_o^{\star}}+n_o.
\end{equation}

This rule is greedy because the choice is made using the current partial
assignment without reconsidering all previous decisions. Its purpose is not to
guarantee a globally optimal schedule, but to avoid concentrating too many
missions on the same resource while respecting eligibility and unique ownership.
The rule used in this work is therefore a deterministic load-balancing heuristic
based on mission count. More refined variants may replace $n_o$ with an
estimated processing time, but the scheduling principle remains the same: among
the admissible resources, new work is preferentially assigned to the resource
with the lowest current load. Since $n_o$ does not depend on the eligible
resource, minimizing $L_r$ is equivalent to minimizing $L_r+n_o$. With
resource-dependent processing estimates, these two choices need not coincide.
The cited online framework distinguishes identical, related, and unrelated
machines, and its guarantees depend on both the model and the algorithm
used~\cite{aspnes1997online}. No competitive-ratio guarantee is claimed here
for the mission-count heuristic under warehouse execution constraints.

A related quantity, evaluated after the simulation with actual execution times,
is the effective workload of resource $r$:

\begin{equation}
	W_r
	=
	\sum_{m:\,r(m)=r} p_m,
	\label{eq:actual-resource-workload}
\end{equation}

\noindent where $p_m$ is the actual processing time of mission $m$. This quantity measures
how much effective work is accumulated by each resource and is therefore useful
for evaluating load balancing. A distinct classical scheduling measure is the
\textit{makespan}, defined as the completion time of the last completed order:

\begin{equation}
	C_{\max}=\max_{o\in\mathcal{O}} C_o.
	\label{eq:makespan-basic}
\end{equation}

\noindent If all resources start from the same temporal origin and no idle intervals are
introduced, $C_{\max}$ coincides with the largest accumulated resource workload;
in the general case, waiting and idle times can make these two quantities
different.

\subsection{Non-preemptive execution and temporal quantities}

The execution considered in this work is non-preemptive. Once a mission starts,
it is allowed to continue until completion; it is not interrupted in order to
serve another mission. Moreover, once an order is assigned to a resource, the
owner is preserved for the entire order. Waiting may occur before the first
mission or between missions because of resource availability, Petri-net enabling
conditions, or path feasibility, but an active mission is not split into
multiple execution intervals.

For an order $o$, the main temporal quantities used in scheduling theory are:

\begin{itemize}
	\item $r_o$: release time, at which the order becomes available for processing;
	\item $S_o$: starting time, corresponding here to the actual start of the
	first mission of the order;
	\item $C_o$: completion time, corresponding to the completion of the last
	mission of the order;
	\item $p_o$: processing time or effective duration required by the order;
	\item $d_o$: due date associated with the order.
\end{itemize}

The flow time includes waiting before execution and is measured from release:

\begin{equation}
	F_o=C_o-r_o.
	\label{eq:order-flow-time}
\end{equation}

The elapsed time from the first actual start is instead $C_o-S_o$. It includes
any waiting between missions and therefore need not equal the effective
processing time $p_o$. These temporal quantities describe execution performance;
they are distinct from the accumulated-load objective of the cited online model.

In a general scheduling problem, the due date $d_o$ can be given externally. In
the present model, instead, it is constructed from an estimated duration and is
anchored to the actual first start of the order. This choice is important because
an order may already be assigned to a resource but remain waiting while that
resource completes previously scheduled work.

\subsection{Estimated processing time and deadline construction}

The processing time of a warehouse order is strongly influenced by spatial
information. Two orders containing the same number of missions may require very
different travel times if their pickup and delivery points are located in
different areas of the warehouse. For this reason, the temporal budget used to
construct the deadline can be based on a geometric estimate of the order rather
than only on its number of missions.

Let $P_r$ denote the current position of resource $r$ when order $o$ starts, and
let $F_i$ and $T_i$ denote the FROM and TO points of the $i$-th mission of the
order. Using a generic geometric distance $d(\cdot,\cdot)$, an estimate of the
travel distance associated with the complete order is

\begin{equation}
	\begin{split}
		\widehat{D}_o ={}& d(P_r,F_1)
		+\sum_{i=1}^{n_o} d(F_i,T_i)\\
		&+\sum_{i=1}^{n_o-1} d(T_i,F_{i+1}).
	\end{split}
	\label{eq:order-geometric-distance}
\end{equation}

\noindent In the current static formulation the distance metric is Euclidean,

\begin{equation}
	d_E(p,q)
	=
	\sqrt{(p_x-q_x)^2+(p_y-q_y)^2}.
	\label{eq:euclidean-distance-scheduling}
\end{equation}

\noindent The geometric distance is then converted into an estimated order duration. If
$v$ is the nominal travelling speed, $\alpha$ is a safety margin applied to the
travel component, $\tau_h$ is a fixed handling time per mission, and $\delta$ is
an additional margin per mission, the estimate can be written as

\begin{equation}
	\widehat{p}_o
	=
	\operatorname{round}\!\left(
	\frac{\widehat{D}_o}{v}(1+\alpha)
	\right)
	+n_o\tau_h
	+n_o\delta.
	\label{eq:estimated-order-processing-time}
\end{equation}

The estimate is not the actual execution time and does not replace path planning.
Its role is to provide a scheduling reference from which the temporal target of
the order can be defined. Once the first mission starts at time $S_o$, the
absolute deadline is fixed as

\begin{equation}
	d_o=S_o+\widehat{p}_o.
	\label{eq:relative-deadline-scheduling}
\end{equation}

Here $\widehat{p}_o$ is a start-relative time budget and $d_o$ is the resulting
absolute target: before the order starts, an absolute due
date is not yet available; when the first mission actually starts, the deadline
is converted into an absolute simulation time. The value is then kept fixed for
the remainder of the order. Recomputing it after every mission would move the
target forward and could artificially hide delays accumulated during execution.

\subsection{Lateness, tardiness and slack}

The comparison between completion time and deadline is described through the
classical concepts of \textit{lateness}, \textit{tardiness}, and \textit{slack}.
The lateness of order $o$ is

\begin{equation}
	L_o=C_o-d_o.
	\label{eq:order-lateness}
\end{equation}

Lateness is a signed quantity: $L_o<0$ means that the order finishes before its
deadline, whereas $L_o>0$ means that the order finishes late. When only positive
delay is relevant, the tardiness is used:

\begin{equation}
	T_o=\max\{0,C_o-d_o\}.
	\label{eq:order-tardiness}
\end{equation}

For consistency with the implementation, the term \textit{completion slack}
denotes the signed margin evaluated after completion:

\begin{equation}
	\sigma_o=d_o-C_o.
	\label{eq:order-slack}
\end{equation}

Hence, a positive slack indicates residual temporal margin, a zero slack means
that the order completes exactly at its deadline, and a negative slack indicates
a deadline violation. Since

\begin{equation}
	\sigma_o=-L_o,
\end{equation}

\noindent the two quantities provide equivalent information with opposite sign.
This retrospective margin differs from the slack used for dispatching an
unfinished order. Given an estimate $\widehat{p}^{\mathrm{rem}}_o(t)$ of its
remaining processing time, the latter can be written as
\[
    s_o(t)=d_o-t-\widehat{p}^{\mathrm{rem}}_o(t).
\]
The completion margin $\sigma_o$ is retained here as an evaluation indicator,
not as a dispatching rule.

When the order has not yet completed, $C_o$ is not available. At a current time
$t$, one may still observe whether the deadline has already been exceeded through

\begin{equation}
	T_o(t)=\max\{0,t-d_o\},
\end{equation}

\noindent but this value represents the current delay of an open order and should not be
confused with the final tardiness, which is known only when the order is
completed.

\subsection{Soft deadlines and scheduling performance measures}

In strict real-time scheduling, a \textit{hard deadline} is a feasibility
constraint: completing after the deadline may make the result unacceptable. In
this warehouse model, the deadline has a different role. Mission execution is not
stopped when the deadline is reached and an order is not discarded simply
because it becomes late. Therefore, although the term \textit{deadline} is used
throughout the implementation, it behaves from a scheduling point of view as a
\textit{soft due date} or service target.

This distinction makes it possible to evaluate the quality of a schedule using
several complementary indicators. Let

\begin{equation}
	U_o=\begin{cases}
		1, & T_o>0,\\
		0, & T_o=0,
	\end{cases}
\end{equation}

\noindent identify a tardy order. The number of late orders is then

\begin{equation}
	N_{\mathrm{late}}
	=
	\sum_{o\in\mathcal{O}} U_o,
	\label{eq:number-late-orders}
\end{equation}

\noindent while the total and maximum tardiness are

\begin{equation}
	T_{\mathrm{tot}}
	=
	\sum_{o\in\mathcal{O}}T_o,
	\qquad
	T_{\max}
	=
	\max_{o\in\mathcal{O}}T_o.
	\label{eq:tardiness-indicators}
\end{equation}

Together with $C_{\max}$ and the distribution of the resource workloads $W_r$,
these quantities describe two different aspects of scheduling performance. Load
balancing measures how evenly work is distributed among the available resources,
whereas deadline-related indicators measure the temporal quality of service
provided to the individual orders.

The scheduling logic adopted in this work is based precisely on this separation.
The initial order assignment uses compatibility and workload information to
obtain a feasible and reasonably balanced distribution, while the temporal layer
records the actual start and completion times and evaluates each order against
its frozen deadline. The Colored Petri Net subsequently enforces the execution
constraints, concurrency, and resource ownership that make the resulting
schedule physically consistent with the warehouse model.
